# フレーム内の判定時計

`GamePlayManager.Update` は、開始予約済みの曲時計を使って既存ノーツの受付可否を更新してから、左右の `SaberCutJudge.RunJudge` を呼ぶ。生成・移動・Miss通知・回収は、その後の従来の `NoteSpawner.Tick` で行う。キャリブレーションも同じ受付更新を通る。

以前は採点が現在の曲時計を見る一方で、受付可否は前フレームの値だった。このため受付開始直後の振りを取り逃し、逆に前フレームから接触中のノーツを受付終了後に切断できた。回数型ロングの最後のカットにも影響していた。

`NoteSpawner.RefreshJudgmentWindows` は受付状態だけを更新する。キャリブレーションの計測・終了、演出、Miss通知の順序を変えず、早め窓・遅め窓・ロング滞留時間の計算を通常の進行処理と共有する。確定済み・切断済み・Miss済みのノーツを再受付しない。開始前の負の予約時刻には対応し、停止後の `SongTime=0` へ巻き戻して更新しない。

これは判定窓・必要速度・空間半径の変更ではない。音源とノーツ到着の約125msの体感ずれについて、全原因が解決したことを意味しない。

## 検証

`GameplayJudgmentClockTests` は本体の `GamePlayManager.Update` を通し、点軌跡とブレード、左右それぞれの判定器、通常ノーツとロングの境界を検証する。修正前の12ケースはすべて失敗した。修正後はキャリブレーション分岐、負の開始時刻、停止後の非巻き戻し、受付更新が移動・Missを発生させないことを含む19ケースが成功した。キャリブレーション分岐の単体テストは計測コントローラー自体の実測を代用しない。

## 別に残る課題

異なる時刻の通常ノーツの正規受付窓が重なる場合、一つの軌跡で両方切れる条件がある。Epilogue Hard の約60.792秒／61.037秒の2ノーツで、点軌跡とブレードの両方式で2切断を再現した。採点や実機操作を再現した試験ではない。

この受付時計の修正だけでは、その重なりは解消しない。一律の「一振り一個」「一振り一時刻」は意図した同時斬りやロング終端からの自然な連続動作を妨げる可能性があるため導入していない。今後の対策では同時刻の複数斬り、左右の独立、金ノーツの左右自由、ロング再進入を保持して評価する。
