# ノーツ・切断処理の軽量化（2026-09-19）

依頼された4項目を実装。譜面、タイミング窓、速度条件、担当する手、方向降格、スコア計算は変更していない。

- 切断片は衝突のない移動・回転・重力アニメーションに変更。切断面は元と同じ平面分割で作り、作業用リストと出力メッシュを再利用する。床や他の破片への跳ね返りは行わない。
- 本編のノーツ、矢印、材質、着地枠、残数表示、ひびを種類別に再利用。ロード時に譜面から必要数を見積もり、ノーツの待機数は128個までに制限する。前の曲だけで使った種類は次の曲へ持ち越さない。破片は64個を事前準備し、待機数を128個までに制限する。表示中に必要な数は確保する。
- 有効なノーツの一覧からセイバー判定を行い、フレームごとのシーン検索と一時リストの生成を廃止。ノーツの世代番号を照合し、前のノーツへの刃の接触や同時線を再利用先へ引き継がない。
- 縁取り4本、各着地枠の4辺、矢印の2本、ロング内部の同じ材質の部品を結合。元の頂点・法線・UV・位置を保つ。色、太さ、矢印の方向、接近枠の収縮は維持する。

各ノーツの状態とイベント購読を初期化し、ミス時の暗い材質やロングの残数を次のノーツへ残さない。プール、メッシュ、材質、独立した残数表示・着地枠は所有するSpawnerの削除やシーン退出時に解放する。タイトル・選曲の単独ノーツも切断の物理簡略化と部品結合を使用するが、本編用ノーツプールの対象には含めない。

## 比較

実際のGameシーンにタップ2個・方向2個・ロング2個を表示した比較で、ノーツと着地枠のRendererは104個から42個（約60%減）。同じ6ノーツの完了直後、切断片のRigidbodyは24個から0個、MeshColliderは12個から0個になった。独立した残数文字、背景、HUDはRenderer集計に含めていない。

切断バーストのCPU時間も記録したが各条件1標本であり、FPS向上率の根拠にはしない。`GC.GetAllocatedBytesForCurrentThread`は両実行で0を返したため、割り当て量の実測結果として扱わない。比較撮影では背景がランダム選択されるため、全画面の画素一致やGPU時間の同条件比較とは扱わない。確認対象はノーツの形状・配置・視認性と、対象部品の数。

## 検証

既存の判定・譜面・シーン試験に加え、連続再利用での二重加算、ミス後の色と残数の復元、古い接触情報、一覧の登録・解除、破片の再利用と解放、結合後の形状、曲切り替え時の種類の入れ替え、複数サブメッシュの切断を検証する。

最終検証はEditMode 979件、PlayMode 105件、合計1084件すべて成功。実機センサー・投影機器でのFPS分布は未測定。
